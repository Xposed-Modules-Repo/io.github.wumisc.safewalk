# 诊断日志怎么读（三区间口径）

这份口径是维护者定的，不是建议：**每份云日志先定位它属于哪一段，再决定拿它干什么**。

| 区间 | 版本号范围 | 用来做什么 |
|---|---|---|
| 基线以下 | `< 基线` | 只作历史参考，**不下「现在是否成立」的结论** |
| 正式版区间 | `基线` → 当前最高开发构建 | 判断问题**是否成立**，只看这一段 |
| 维护者本机 | 最新构建（`is_dev = 1`） | 只用它**验证规则本身**，不当用户证据 |

- **基线**：GitHub 上最新一次正式 Release 的 `versionCode`。下次发正式版，基线自动抬到它，之前那些开发构建自动进入正式版区间。
- **跨区间对比**：同一个问题同时出现在两段以上时，按「基线以下 → 正式版 → 开发上限」三列摆开，结论只认**正式版与开发版之间有没有改善**。
- **低于基线的样本不证明任何事**：它只能说明「当时是这样」，不能说明现在修好了没有。
- **维护者本机（白名单）**：`is_dev = 1` 的行默认被 `GET /api/diag/list` 排除；要自查就加 `?include_dev=1`。统计用户问题时绝不能把这台机器的记录混进去——它永远跑最新构建。
- **不按 versionCode 清理**：后端保留策略只按「厂商 + 机型 + 来源 IP」留最近 3 条。按版本号清会把别人在旧正式版上的反馈整组删掉。

## 怎么取数

```bash
# 只看用户（默认排除白名单本机），含短码、版本、区间字段
./tools/bands.sh

# 连维护者本机一起看（自查用）
./tools/bands.sh --include-dev
```

`tools/bands.sh` 会先问 GitHub 要当前基线，再把每条记录盖上 `band` 字段（`below` / `release` / `dev`），最后按机型分三列打印。全文日志仍需 `wrangler d1 execute` 取（list 接口只回 200 字符头部）。

## 每条记录该看什么

1. **先看 `band`**：`below` 直接跳过结论，`dev` 只用来自查。
2. **再看 `version_code` 是否 ≥ 基线**：小于就是历史样本。
3. **同问题对比**：`release` 里还有 → 问题成立；只有 `below` 里有 → 已经修了（但要确认修复落在哪个构建）。
4. **短码**：用户报「短码 3F2A91C4」时，直接 `WHERE log_hash LIKE '3f2a91c4%'` 定位那一行，不用让用户念机型。
