# 行走模式保活与自动恢复（4.4.0）

> 面向用户与后来维护者。本文件只讲「通知为什么会消失、消失后会发生什么、哪些情况我们确实做不到」。
> 状态：代码与静态核对完成，**未真机复现「杀进程 → 自动恢复」**，因此下文所有能力均按 🟡 记录。

## 一、先分清「通知消失」的三种原因

锁屏上那条 `行走模式运行中 / 身后路况持续显示中` 是 [WalkPreviewService] 的**前台服务通知**。
它是用户判断「功能还在不在」的唯一可见信号，但它并不总等于服务的真实状态：

| 现象 | 服务真实状态 | 系统行为 | 4.4.0 的处理 |
| --- | --- | --- | --- |
| 进程被 ROM / 低内存回收 | **真的停了** | 系统连带撤销前台服务通知 | 看门狗自动拉起，通知重新出现，并发一条「已自动恢复」 |
| `safewalk_walk` 通知渠道被关 / 被 ROM 折叠 | **还在跑** | 服务活着，但通知一条都不显示 | 换 HIGH 渠道提示「服务其实还在」，并给出通知设置入口 |
| `startForeground()` 三档降级全部失败 | 半停（随时被杀） | 没有前台通知，进程优先级最低 | 保持原有日志与电池白名单建议，不假装成功 |

把第 2 种当成第 1 种，会让用户反复去拨一个本来开着的开关；把第 1 种当成第 2 种，则会
一路走到路口才发现身后画面早没了。所以这一版不只做「复活」，也把这两种情况显式拆开。

## 二、4.3.1 之前为什么「保活不够」

| 手段 | 实际情况 |
| --- | --- |
| `START_STICKY` | 国产 ROM 一键清理、电池优化、划掉任务后基本不重建 |
| Hook 开机自启 | `autoStartLaunched` 是**一次性**标志，每个 SystemUI 进程只拉一次透明页 |
| Hook 每 60 秒补发 `ACTION_HOOK_SHOW` | 发给 App 的**动态**接收器；进程死了就没人收，也拉不起进程 |
| 开机 / 解锁 / 覆盖安装 / 划任务静态兜底 | **不存在** |
| 常驻通知可点击 / 渠道自检 | **不存在**（点了没反应，渠道被关也不会告知） |

结论：只要 App 进程被杀一次，就再没有任何一条路径会把它拉回来，除非用户自己打开 App。

## 三、4.4.0 的机制

### 3.1 主力：SystemUI 看门狗

本项目有一个别的应用没有的条件 —— LSPosed 把 Hook 注入了 **SystemUI 进程**，它几乎不会被回收，
而且本来就每 2 秒巡检一次。把它当外部监护者，比在 App 进程内做任何「防杀」都可靠：

```
WalkPreviewService（App 进程）
   │ onCreate → 立刻发一次心跳，之后每 30s 一次
   │ ACTION_HEARTBEAT  ──显式广播──▶  Hook（SystemUI 进程）
   │                                  │ 记录 lastHeartbeatAt（elapsedRealtime，单调）
   │                                  │ 每 2s：desired && 心跳超时 90s
   │                                  │   → startActivity(AutoStartActivity, 透明)
   │                                  ▼
   └────────◀── startForegroundService ── AutoStartActivity（本应用有可见 Activity）
                                           → goForeground() → 通知重新出现
```

`AutoStartActivity` 是 Android 14/15 上唯一稳定豁免（启动瞬间应用有可见 Activity）；
从广播或闹钟里直接 `startForegroundService` 一个 camera 类型 FGS 会被
`ForegroundServiceStartNotAllowedException` 拦下，所以两条腿都统一走透明页。

判定与冷却全部抽成 [KeepAlivePolicy]（纯 Kotlin、无 android 依赖、15 条 JVM 单测）：

| 常量 | 值 | 理由 |
| --- | --- | --- |
| 心跳周期 | 30s | 一条本地广播，成本远低于 Hook 的 2s 巡检 |
| 心跳超时 | 90s | 容得下连续丢 2 条广播，避免偶发丢包误判 |
| 正常复活冷却 | 60s | 拉起后给服务时间完成 `startForeground` 并发第一条心跳 |
| 盲区冷却 | 180s | 心跳通道完全不通时压低重试频率，防止每 90s 闪一次透明窗 |
| 开机宽限 | 5s | 等 SystemUI 完成 init 与接收器注册 |

### 3.2 第二条腿：静态兜底

[KeepAliveReceiver] 覆盖框架没加载 / SystemUI 正在重启的空窗：

| 时机 | 动作 |
| --- | --- |
| `BOOT_COMPLETED` | 开机静默恢复 |
| `MY_PACKAGE_REPLACED` | 覆盖安装杀进程后恢复 |
| `USER_PRESENT` | 解锁时自检，服务不在就恢复（Android 8+ 隐式广播限制下可能被拦，属尽力而为） |
| `ACTION_REVIVE`（`onTaskRemoved` 排的 1.5s 自检闹钟） | 划掉任务后**先查 `isAlive()`，真不在才恢复**，并弹一条回执 |

### 3.3 通知本身的加固

- **可点击**：常驻通知补了 `contentIntent`，点一下回主界面（原来点了没反应，用户容易顺手去划它）。
- **渠道自检**：`goForeground()` 读回渠道 importance，若为 `IMPORTANCE_NONE` 就换
  `SafeWalkNotificationManager` 的 HIGH 渠道发一条说明，点击直达「应用通知设置」。
- **恢复回执**：被杀后重新拉起会弹「行走模式已自动恢复」，由 SP 时间戳节流，10 分钟最多一条。

## 四、明确做不到的（不要写成「保证不杀」）

1. **用户手动「强制停止」后不会复活**。系统把应用标成 STOPPED，静态广播与闹钟都不再投递。
   这是系统语义，也是用户意图，不绕过。
2. **ROM 深度清理 / 未加电池白名单仍可能杀进程**。本机制是「被杀后尽快自己起来」，不是「永不被杀」。
   白名单、自启动、后台弹出界面这三项仍需用户按 [docs/rom-adaptation-plan.md](rom-adaptation-plan.md) 配好。
3. **从广播 / 闹钟里拉透明页受 Android 10+ 后台启动 Activity 限制**，可能被拦。
   `try/catch` 记日志即可，主力仍是 SystemUI 看门狗（它从系统进程发起，不受此限制）。
4. **心跳通道可能不通**。广播显式投递到 `com.android.systemui`，并补一条 `com.miui.systemui` 变体；
   若某 ROM 用了第三种包名，Hook 会一条也收不到，此时进入「盲区」模式把重试压到 3 分钟一次，
   **不会**每 90 秒闪一下透明窗。代价是恢复慢一些，不会变成骚扰。
5. **没有真机验证**。本轮只有静态核对、184 条单测（新增 15 条）、lint 与 APK 产物校验。
   「杀进程 → 90 秒内自动恢复」这条链路尚未在真机上跑通，矩阵里标 🟡。

## 五、怎么确认有没有生效

`diag.log`（`Android/Travel safely/`）里搜 `[keep]`：

| 日志 | 含义 |
| --- | --- |
| `收到预览服务心跳（本进程已复活 N 次）` | 心跳通道正常，2 分钟一条节流日志 |
| `看门狗判定预览服务失联（…）→ 拉起透明页恢复` | 判定服务已死，正在复活 |
| `AutoStart：已请求启动预览服务（fromRevive=true）` | 透明页已代启服务 |
| `行走模式已自动恢复（系统曾回收预览进程）` | 复活完成，已发回执 |
| `最近任务被移除 → 已排 1.5s 后自检预览服务` | 划任务兜底已排期 |
| `恢复请求被系统拦截（后台启动限制）` | 静态兜底这一次没成功，等看门狗 |

如果在华为 / 荣耀 / 三星等机器上实测，把 `[keep]` 与 `[FGS]` 附近的日志发回，可以据此判断
该补哪个 SystemUI 包名、或者是否需要调整心跳超时。
