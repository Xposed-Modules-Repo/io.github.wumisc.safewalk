# 无障碍能力边界与读屏增强方案

> 拟稿：2026-11-13（4.8.0）｜状态：**方案已定，读屏助手本体待实施**
> 相关代码：`SafeWalkA11yService.kt`、`A11yInspectorService.kt`、`WalkVoicePolicy.kt`

---

## 0. 先给结论

**无障碍服务无法替代 LSPosed + root。** 这两者是不同的能力层，不是新旧关系。

正确架构是**双通道并存**：

| 通道 | 前提 | 能力 | 现状 |
|------|------|------|------|
| **Hook 通道** | LSPosed + root | 在 SystemUI 进程内改行为：通知栏、状态栏、锁屏、最近任务、系统弹窗 | 既有能力，保留 |
| **无障碍通道** | 仅需用户授权 | 观察前台应用、读通知、模拟手势、读节点树 | 4.8.0 已补两块 |

有 root 的用户走 Hook，能力全；无 root 的用户走无障碍，覆盖日常场景。**不是替代，是降级可用。**

---

## 1. 能力对照（为什么会这样）

| 能力 | Hook（SystemUI 进程内） | 无障碍服务 | 说明 |
|------|------------------------|-----------|------|
| 感知前台应用 | ✅ | ✅ `TYPE_WINDOW_STATE_CHANGED` | 已替代 |
| 读取通知内容 | ✅ | ✅ 通知事件 | 可替代（需开关，见下） |
| 模拟点击 / 滑动 | ✅ | ✅ `dispatchGesture` | 可替代 |
| 读屏幕文字 / 节点树 | ✅ | ✅ 需 `canRetrieveWindowContent` | 可替代 |
| **修改其他 App 的节点树** | ✅ | ❌ **节点是只读快照** | **不可替代** |
| **Hook SystemUI 内部方法** | ✅ | ❌ | **不可替代** |
| **拦截系统弹窗** | ✅ | ❌ | **不可替代** |
| **静默授予权限 / 安装** | ✅ | ❌ | **不可替代** |

### 1.1 为什么「改节点树」做不到

`AccessibilityNodeInfo` 是从目标进程**拷贝**出来的一份快照。你在自己进程里对它调
`setContentDescription()`，改的只是这份副本，目标 App 根本不知道，TalkBack 下次
拿到的仍是原始节点。

系统没有提供任何「无障碍服务向目标 App 回写节点属性」的接口——这是设计上的隔离，
不是版本限制。

### 1.2 所以「OCR 补描述喂给 TalkBack」这条路走不通

原需求是「自动识别按钮文字、图片 OCR 补描述，喂给 TalkBack」。前两步（识别、补描述）
能做，**最后一步做不到**。

可行的替代只有两种：

1. **自己的 TTS 播报**：读到无描述控件 → 推断语义 → 自己念出来。不与 TalkBack 冲突，
   稳定可控。← **本轮选定**
2. **叠加透明层**：在目标控件上盖一个带 `contentDescription` 的透明 View，诱使 TalkBack
   读它。技术上脆弱：双重焦点、坐标漂移（滚动/缩放即失效）、部分 ROM 直接不生效。

第二条会制造比原问题更糟的体验，**不做**。

## 2. 本轮已交付

### 2.1 无障碍调试面板（开发者工具）

`A11yInspectorActivity` + `A11yInspectorService`，独立授权、默认不采集。

- 事件流：全类型事件，带时间、来源包名、控件类名、文本
- 节点树：层级、文本、contentDescription、viewId、可点击性、屏幕坐标
- **无标签统计**：可点击但既无 text 也无 desc 的节点数——这就是读屏增强要补的目标

隐私边界：`onResume` 才采集、`onPause` 立即停；只进内存环形缓冲（300 条），
不写文件、不联网。

### 2.2 行走语音播报（视力障碍）

复用主服务 `SafeWalkA11yService`，开关打开时动态订阅通知事件。

闸门（全部有单测）：只在行走中、只在亮屏、尊重勿扰、全局 15s 冷却、同源 60s 冷却、
只识别来电与即时消息。详见 `WalkVoicePolicy.kt`。

## 3. 读屏助手（下一批实施）

### 3.1 形态

独立助手，**不接管 TalkBack**：

```
用户手势 / 悬浮按钮
      ↓
读当前窗口节点树（复用 A11yInspectorService.dumpActiveTree）
      ↓
语义增强（见 3.2）
      ↓
TTS 播报：「当前屏幕有 5 个按钮：返回、搜索、设置、更多、关闭」
```

不叠层、不改 TalkBack 焦点，用户可以随时关掉，也可以和 TalkBack 同时开（各说各的，
但互不干扰）。

### 3.2 无 OCR 的语义增强策略（本轮确认不做 OCR）

按信息可信度从高到低：

| 优先级 | 线索 | 处理 |
|--------|------|------|
| 1 | `text` 非空 | 直接用 |
| 2 | `contentDescription` 非空 | 直接用 |
| 3 | `viewIdResourceName` 含语义 | `btn_back` → 「返回」、`iv_search` → 「搜索」 |
| 4 | 相邻兄弟/父节点有文本 | 借用（列表项标题 + 按钮的组合很常见） |
| 5 | 类名 + 位置 | `ImageView` + 右上角 → 「右上角按钮」 |
| 6 | 都没有 | 播「未命名按钮，第 N 个」 |

第 3 条需要一份**图标语义表**（`btn_back/iv_close/ic_search/...` → 中文），
这是纯数据，可以持续补，且零体积代价。这是本轮选「不引入 OCR」的底气：
绝大多数「按钮没文字」其实是**图标按钮**，靠 id 与类名就能覆盖。

OCR 的接入点已经留好：`A11yNode` 增加 `ocrText` 字段，语义链在第 3 与第 4 条之间插入
「图片区域 OCR」即可，不需要改上层逻辑。

### 3.3 触发方式

- 悬浮按钮（可拖动、半透明、可关闭）
- 或音量键组合（需无障碍服务拦截按键，与部分 ROM 冲突，作为备选）

默认悬浮按钮，因为按键拦截在国产 ROM 上成功率不稳定。

## 4. 已知边界（诚实清单）

1. **无法修改 TalkBack 读的内容**——只能自己念，这是 Android 的设计约束。
2. **`FLAG_SECURE` 窗口读不到**——银行、支付类 App 常设，节点树为空是正常现象。
3. **TTS 依赖系统语音引擎**——精简 ROM 可能没有，此时静默降级（日志留痕）。
4. **语音播报只认白名单 App**——未收录的即时通讯 App 不会播，需要往
   `WalkVoicePolicy.MSG_PKGS` 里加。
5. **无障碍服务被杀后需用户重新开启**——系统行为，无法自恢复。
6. **本轮全部未真机验证**——结论来自编译、单测与静态检查。

---

## 5. 为什么不做「完全替代 root」的路线

即使把无障碍能做的事做到极致，仍有四件事永远做不到：改 SystemUI、拦截系统弹窗、
静默授权、修改其他 App 状态。而 SafeWalk 的核心价值（通知栏常驻、锁屏表现、
系统级提醒）恰恰依赖前两项。

所以路线是**保住 Hook 通道，把无障碍做成「没 root 也能用」的降级层**，
而不是把两者对立起来。用户装不装 LSPosed，决定的是能力上限，不是能不能用。
