## 二、常驻高耗电组件

1. **相机前台服务 + 预览会话**（`camera|specialUse` 前台服务 + `setRepeatingRequest` 持续出帧）——功耗最大头，但这是行走模式的核心功能，属于"必要的耗电"。
2. **RenderEffect / AGSL 着色器**：画面增强开启时逐帧后处理；关闭即置 null，无常驻开销。
3. **多路传感器并行**：加速度 + 姿态 + 计步同时监听，其中姿态与步态各有独立采样。
4. **诊断日志 I/O**：默认开启，每条日志都 `new FileOutputStream` 追加并 close，高频 tick 下 I/O 唤醒可观。
5. **保活心跳 + 到位定位**：30s 广播与 60s 定位属于周期性后台唤醒。

机制已到位、**无需改动**的点：
- 相机类应用切到前台时会 `closeCamera()` 让路（`RearCameraOverlay.kt:963`，由 A11y 触发），避免抢摄像头和黑屏，逻辑正确。
- 画面增强关闭时释放 RenderEffect，无常驻开销。
- 无 WakeLock 滥用、无常驻动画循环。

## 三、本次已落地的省电优化（低风险）

| # | 改动 | 位置 | 收益 | 风险 |
|---|---|---|---|---|
| 1 | 总开关关闭时，Hook 巡检间隔 5s → 30s | `SafeWalkLSPHook.kt:1489` | 关闭态唤醒次数降为 1/6，长期待机省电明显 | 低：关闭态本无功能输出；打开开关由 `configChangedReceiver` 即时响应，不依赖 tick |
| 2 | 姿态监听采样率 UI(~60ms) → NORMAL(~200ms) | `RearCameraOverlay.kt:580` | 传感器唤醒减少约 3 倍 | 低：只需判横竖，迟滞/驻留本就在策略层做，200ms 延迟用户无感 |

两项改动均不改变核心判定逻辑（步态、车祸、保活链路原样保留），可在真机上直接回归。

## 四、暂缓 / 需谨慎评估的优化（本版未改）

| 项 | 为何暂缓 |
|---|---|
| DiagLog 改批量缓冲写盘 | 日志是本项目诊断核心，用户依赖它回传排查；批量化会影响实时性与尾部完整性，需配套"回传前强制 flush"，改动面较大，建议单独迭代并真机验证 |
| 步态复核 GAME → NORMAL | 该采样仅 4.6s，用于快速采够波形做复核；降采样会减少样本、影响复核准确性，不建议改 |
| gaitTick 1s 拉长 | 与 30s 步态窗口的静置判停耦合，改周期会影响判停延迟，需重测 |
| 到位定位按需启用 | 涉及出行模式识别链路与后台定位权限，改动语义较大，需真机回归 |
| 相机预览会话超时调整 | 已有相机应用前台让路机制，贸然改超时会破坏让路稳定性 |

## 五、结论

本次落地 2 项低风险省电优化，主要削减**关闭态空转唤醒**与**姿态传感器采样密度**，不触及步态判定、车祸预警、相机让路等核心链路。其余高收益但高风险的改动（日志批量写、定位按需、相机会话策略）已列出明确方案，建议在具备真机回归条件时单独迭代。
