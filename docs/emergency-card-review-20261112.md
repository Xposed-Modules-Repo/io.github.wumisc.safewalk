# 急救卡体检与重构说明（2026-11-12）

对象：`EmergencyCardActivity` + `activity_emergency.xml` + `EmergencyAlertActivity` 链路
版本：4.7.0（49）

## 一、体检结论（重构前）

| 环节 | 能否正常工作 | 问题 |
|------|------------|------|
| 表单填写与回显 | ✅ 正常 | 5 个字段读写一致，历史上「身高/体重框写进电话」的错位已修 |
| 保存 | ⚠️ 有丢数据风险 | 用 `apply()` 异步落盘，点完立即退出/被杀可能没写进去 |
| 输入校验 | ❌ 无 | 全空也能「保存成功」，得到一张对救援毫无意义的空卡 |
| 医疗信息完整度 | ⚠️ 不足 | 缺「过敏史」「慢性病/用药」——恰是急救时最关键的两项 |
| 锁屏可及性 | ❌ 文案与事实矛盾 | 页面写「手机损坏时救援人员可直接查看」，但锁屏打不开 App，这句做不到 |
| 车祸预警权限 | ⚠️ 状态不透明 | 授权失败只改一句提示，用户不知道到底缺哪个权限 |
| SOS 跳转 | ✅ 基本正常 | 5 个厂商路径 try/catch 兜底到系统设置，能到得了 |

结论：**基础读写链路是通的**，但在「真出事时能不能救命」这个标准下有三处硬伤——
保存可能丢、空卡能存、承诺了锁屏看得到。

## 二、重构后的设计逻辑

### 1. 保存：commit + 最小校验

- `apply()` → `commit()`：急救信息属于「写完就得算数」的数据，不能等异步。
  同时保证紧随其后的 `exportConfig()` 读到的是已落盘值。
- 校验规则：
  - 姓名与联系人电话**都为空 → 拒绝保存**（空卡没有意义）；
  - 电话填了但有效数字 < 5 位 → 提示检查；
  - 其余字段不强制，避免用户在紧急场景被表单卡住。

### 2. 信息完整度：补两项医疗关键字段

新增「过敏史」「慢性病 / 长期用药」，多行输入。这两项在真实急救里比住址更关键
（用药冲突、过敏反应直接决定处置方式）。

### 3. 锁屏可及性：说真话 + 给可落地路径

- 明确写出「锁屏时别人看不到这张卡」，不再承诺做不到的事；
- 新增**一键复制急救信息**：把姓名/血型/过敏/慢病用药/住址/联系人拼成一段文本，
  用户粘贴进系统「紧急信息 / 医疗急救信息」——那才是锁屏可见、救援人员能读到的。

> 这是本次重构里对「更安全」贡献最大的一条：不是把 App 内页面做得多漂亮，
> 而是把信息送到真正能被看到的地方。

### 4. 车祸预警：权限状态可视化

新增「权限 X/4 · 缺少：打电话/发短信/定位」，已授权显示绿色、缺权限显示橙色。
解决「以为在监测，其实没授权」的错觉。

### 5. 隐私边界不变

急救卡全部字段（姓名 / 血型 / 住址 / 联系人 / 过敏 / 用药）**仍不进入**
`ConfigProvider` 白名单，不跨进程暴露给 SystemUI。新增字段同样不导出。

## 三、明确未做的事

1. **没做 App 内「救援预览页」**：`EmergencyAlertActivity` 已是带倒计时的弹窗，
   再加一个纯预览页收益低、维护成本高。
2. **没改车祸检测算法**：`CrashDetector` 与灵敏度映射未动，本轮只做信息与交互层。
3. **没做自动填系统紧急信息**：系统「医疗信息」没有公开写入 API，只能引导用户复制粘贴。
4. **没做真机验证**：权限弹窗、剪贴板、锁屏可见性均需真机确认。

## 四、仍存在的限制

- 车祸预警依赖 SystemUI 进程存活与传感器，ROM 强杀后不会监测（页面已如实提示）。
- 「复制急救信息」依赖剪贴板权限，部分 ROM 后台读剪贴板有限制，但写入一般不受影响。
- 急救卡信息仍是明文存于应用私有 SharedPreferences，未加密；root 设备可读。
